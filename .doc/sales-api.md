# Sales API contract

## Scope and status

This document is the implementation contract for the sales API. Domain code, persistence, controllers, and tests must conform to this contract.

The challenge README is authoritative for the required sale fields, CRUD operations, and quantity-based discounts. The rules identified as **project decisions** below resolve behavior that the README does not define so that implementation and tests have one consistent target.

The machine-readable contract is available at [openapi/sales.yaml](openapi/sales.yaml). Runnable request examples are available in [`Ambev.DeveloperEvaluation.WebApi.http`](../src/backend/Ambev.DeveloperEvaluation.WebApi/Ambev.DeveloperEvaluation.WebApi.http).

## Required behavior

A sale records:

- a unique sale number;
- the sale date;
- customer and branch snapshots;
- one or more product lines;
- quantity and unit price for each line;
- discounts and calculated totals;
- sale and item cancellation state.

The API provides create, retrieve, list, update, delete, sale cancellation, and item cancellation operations.

### Discount rules

Discounts are calculated by the API for each line. Clients cannot submit rates or calculated amounts.

| Quantity of one product | Discount | Result for BRL 10.00 per unit |
|---:|---:|---:|
| 1–3 | 0% | 3 × 10.00 = 30.00 |
| 4–9 | 10% | 4 × 10.00 − 4.00 = 36.00 |
| 10–20 | 20% | 10 × 10.00 − 20.00 = 80.00 |
| 0 or more than 20 | Invalid | Request rejected without a write |

The README says both “above 4” and “4+” in different places. **Project decision:** the explicit tier table wins, so exactly four units receive a 10% discount.

For every line:

```text
grossAmount = quantity * unitPrice
discountRate = 0, 0.10, or 0.20
discountAmount = Round(grossAmount * discountRate, 2, AwayFromZero)
totalAmount = grossAmount - discountAmount
effectiveAmount = isCancelled ? 0 : totalAmount
sale.totalAmount = sum of every effectiveAmount
```

Money uses decimal arithmetic and two fractional digits. The discount is rounded once per line. `float` and `double` are not valid persistence or domain representations for money.

## Project decisions

The following decisions are required for a deterministic implementation but are not explicit challenge requirements:

| Topic | Decision |
|---|---|
| Currency | BRL only; taxes, shipping, and currency conversion are outside this delivery. |
| Sale number | Client-provided, trimmed, uppercased, globally unique, and immutable. Length: 1–50 characters. |
| External identities | Customer, branch, and product are stored as `externalId` plus `name` snapshots. No foreign key to another domain is required. |
| External IDs | Trimmed opaque strings, case-sensitive, 1–100 characters, with no control characters. |
| Snapshot names | Trimmed strings, 1–200 characters. Existing historical product snapshots are immutable. |
| Duplicate product | A product external ID can occur only once in a sale, including cancelled lines. Duplicate lines are rejected. |
| Quantity | Integer from 1 through 20 per product line. Zero is not a cancellation command. |
| Unit price | Greater than zero, at most BRL 1,000,000.00, with at most two fractional digits. |
| Sale date | ISO 8601 timestamp with an explicit offset, normalized to UTC. More than five minutes in the future is rejected. |
| Audit dates | `createdAt`, `updatedAt`, and cancellation/deletion timestamps are generated by the server. |
| Sale size | Creation requires at least one item. A sale contains at most 100 total lines, including cancelled lines. |
| Cancelled sale | Cannot be edited, extended, or reactivated. Cancellation is irreversible in this delivery. |
| Item cancellation | Cancels the complete line and retains its historical quantity, price, discount, and totals. |
| Last active item | Cancelling it automatically cancels the sale. |
| Deletion | `DELETE` performs a soft delete. It is separate from cancellation and hides the sale from public reads. |
| Authorization | `Manager` and `Admin` may operate sales. `Customer` has no access to the sales module. |

Historical descriptions do not change when an external customer, branch, or product changes. Updating a sale may replace its customer or branch snapshot. An existing product line may change quantity and price, but not product identity or its historical description.

## Operations

| Method and route | Success | Behavior |
|---|---|---|
| `POST /api/sales` | `201 Created` | Returns the created sale, `Location`, and `ETag`. |
| `GET /api/sales/{id}` | `200 OK` | Returns the sale including cancelled lines and an `ETag`. |
| `GET /api/sales` | `200 OK` | Returns paginated summaries without item collections. |
| `PUT /api/sales/{id}` | `200 OK` | Replaces editable sale data and active lines; requires `If-Match`. |
| `POST /api/sales/{id}/cancel` | `200 OK` | Cancels the sale; requires `If-Match`. |
| `POST /api/sales/{id}/items/{itemId}/cancel` | `200 OK` | Cancels one line; requires the sale `If-Match`. |
| `DELETE /api/sales/{id}` | `204 No Content` | Soft-deletes the sale; requires `If-Match`. |

All operations require bearer authentication and the `Manager` or `Admin` role.

### Update semantics

`PUT` accepts `saleDate`, `customer`, `branch`, and the complete collection of active items. It does not accept `saleNumber`.

Existing active lines include their internal `id`. New lines omit `id`. The request must include every active line currently in the sale. Omitting an active line is invalid because cancellation must use the explicit cancellation endpoint. Cancelled lines are omitted from the request and remain unchanged.

An item ID is invalid when it is duplicated, unknown, cancelled, or belongs to another sale. The API validates the complete candidate state before changing the aggregate.

Submitting content identical to the current state with the current version returns the current resource without incrementing the version or publishing an event. A stale version returns `412 Precondition Failed` even when the submitted content is otherwise identical.

### Cancellation and deletion

Cancelling an already cancelled sale or item with the current version succeeds without another mutation or event. A stale version still returns `412`.

Cancelling a sale cancels every active item. Cancelling the last active item also cancels the sale. Cancellation retains historical amounts; cancelled lines contribute zero to the sale effective total.

Deleting a sale does not mean cancelling it. A deleted sale is retained as a tombstone and is absent from public list and detail operations. A repeated delete with the last valid pre-deletion ETag returns `204`; another token returns `412`. A UUID that never existed returns `404`.

## Optimistic concurrency

Every sale has a numeric internal version represented externally by a strong, opaque `ETag`. Clients must treat the ETag as an opaque value.

Mutating existing resources requires one `If-Match` token previously returned by the API:

- missing `If-Match`: `428 Precondition Required`;
- malformed token or wildcard: `400 Bad Request`;
- stale token: `412 Precondition Failed`.

Every successful mutation increments the sale version, including item mutations. A no-op cancellation or update keeps the current version.

## Listing, filtering, and ordering

`GET /api/sales` supports:

- `_page`: positive integer, default `1`;
- `_size`: positive integer, default `10`, maximum `100`;
- `_order`: comma-separated allowlisted fields and directions;
- `saleNumber`;
- repeated `customerExternalId`, `branchExternalId`, and `isCancelled` values;
- `_minSaleDate` and `_maxSaleDate`;
- `_minTotalAmount` and `_maxTotalAmount`.

Allowed ordering fields are `saleDate`, `saleNumber`, `totalAmount`, and `id`. A missing direction means ascending. The default is `saleDate desc,id asc`, and `id` is always added as the final stable tie-breaker.

Different filters use logical AND. Repeated values for the same equality filter use logical OR, with at most 20 values. Ranges are inclusive. Unknown, duplicated range, malformed, or inverted parameters return `400`.

`saleNumber` supports one optional `*` at the beginning, end, or both. Interior wildcards, an empty pattern, or only `*` are invalid. External IDs use exact equality after trimming.

```json
{
  "data": [],
  "totalItems": 0,
  "currentPage": 1,
  "totalPages": 0
}
```

A page beyond the final page returns an empty `data` array with the real counts. Zero matching rows produce `totalPages: 0`.

## Error contract

Errors follow the fields defined in [general-api.md](general-api.md) and add correlation and field details when available.

```json
{
  "type": "ValidationError",
  "error": "Invalid input data",
  "detail": "Correct the fields listed in errors.",
  "traceId": "00-a92b8e7d0a6c4382a89c82e68071391b-0de9de32bd4f6778-00",
  "errors": [
    {
      "field": "items[0].quantity",
      "code": "QuantityOutOfRange",
      "message": "Quantity must be between 1 and 20."
    }
  ]
}
```

| Status | Use |
|---:|---|
| `400` | Invalid JSON, binding, input rules, duplicate products, malformed ETag, or unsupported query syntax. |
| `401` | Missing or invalid authentication. |
| `403` | Authenticated identity without the required role. |
| `404` | Unknown/deleted sale or an item that is not part of the addressed sale. |
| `409` | Duplicate sale number or a state transition forbidden by the current sale state. |
| `412` | Stale `If-Match` token. |
| `413` | Request body larger than 256 KiB. |
| `415` | Unsupported request content type. |
| `428` | Required `If-Match` header is absent. |
| `429` | Request rate limit exceeded. |
| `500` | Unexpected server error without internal implementation details. |
| `503` | A required dependency is unavailable. |

Creation with an existing normalized sale number returns `409`. It is not an idempotent replay of the first response. Persistent `Idempotency-Key` support is a future extension.

## Requirement traceability

| Contract area | Implementation task | Primary verification |
|---|---|---|
| Discount tiers, quantity limits, totals, duplicate products | T03 | Unit and property-oriented domain tests |
| Persistence, uniqueness, decimal precision, concurrency token | T04 | PostgreSQL integration tests |
| Create, detail, and update operations | T05 | Application and HTTP tests |
| Listing, filters, ordering, and pagination | T06 | Query integration and HTTP tests |
| Sale/item cancellation and soft delete | T07 | Domain, persistence, and HTTP tests |
| Error format, authorization, request limits | T08 | Functional security and failure tests |
| Optional events | T09 | Post-commit event tests |

Event publication remains optional under the challenge README. `SaleCreated`, `SaleModified`, `SaleCancelled`, and `ItemCancelled` are logged only after a successful commit with an event ID, sale ID, aggregate version, occurrence time, and correlation ID. A publishing failure is logged without reporting the already committed sale write as rolled back.

This delivery is best effort. A process failure between the PostgreSQL commit and the structured log can lose an event. Durable delivery through a transactional outbox is a separate extension and is not guaranteed by this contract.
